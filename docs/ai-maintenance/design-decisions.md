# 设计依据与可靠性边界

这份文档说明当前实现的设计原因和可靠性边界。接口和配置细节分别见 [架构](architecture.md) 与 [配置说明](configuration-and-secrets.md)。

## 关键设计

| 设计 | 原因 | 维护要求 |
|---|---|---|
| 原始邮件备份优先 | 邮件需要完整归档，摘要和通知可以稍后处理 | AI、Telegram、缓存和告警失败不得撤销已经完成的备份 |
| Gmail 使用 `users.messages.insert` | 直接写入原始 MIME，减少二次投递受到认证和反垃圾策略影响的机会 | 保留原始字节与附件，使用用户 OAuth 授权 |
| Gmail 失败后依次尝试 Cloudflare Email Sending 和 Resend | 在主备份不可用时尝试保存原件 | 兜底邮件必须附带 `original.eml`；供应商接受发送后停止备份链，最终投递仍需关注 |
| 按阶段记录处理状态 | 邮件重试时，已完成的备份和待完成的通知需要分别处理 | 读取到 `backup_done=true` 时跳过备份，继续处理未完成的通知或告警 |
| 通知由后台任务即时尝试，Cron 后续补偿 | 通知失败不应使整封邮件重新备份 | 保存状态和正文，让后续执行能够接手 |
| 原文只在本人 Bot 私聊中查看 | 邮件正文和 Gmail 操作需要访问控制 | 同时检查 webhook secret、私聊类型、chat ID、点击者 ID 和消息映射 |

## 原件保存与状态写入

Gmail 通过 multipart media upload 上传原始字节，避免将整个原件放入 JSON 的 base64 字段后额外增加体积。MIME 解析失败或超过解析阈值时，备份仍使用原始字节；兜底正文中的占位说明不能代替原件附件。

供应商调用和 KV 状态保存分别处理异常。供应商已经确认成功后，KV 写入失败不能触发另一家供应商再次发送。成功结果保留在当前执行的状态中，通知阶段保存状态时会再次写入。处理状态、正文缓存和消息映射遇到 KV 写入 429 时，等待 1 秒后重试一次。

原始邮件会完整读入内存，`MAX_PARSE_BYTES` 只限制 MIME 解析。上传方式和解析降级无法消除 Worker 内存、执行时间及供应商大小限制。

## 通知恢复

首次处理状态初始化 `telegram_done: false`、通知缓存 ID 和下一次补偿时间，让 Cron 能在后台通知中断后识别待处理邮件。

原件备份完成后，先保存可读正文，再进入后台摘要任务。Cron 仅为已完成备份的邮件补偿摘要通知：缓存已有摘要时优先复用，只有正文时重新生成摘要，并恢复相应的结果字段。备份失败告警按各自状态补偿。

Cron 恢复依赖已经保存的状态和缓存。KV 持续不可写或缓存已过期时，定时任务无法从未保存的数据中恢复通知。供应商已经确认成功的原件备份仍然保留。

## Telegram 与摘要输出

“删邮件+消息”只在 Gmail 主备份成功时出现。先处理 Gmail。查询返回 404 或已有 `TRASH` 标签时，视为 Gmail 操作已完成；否则移入垃圾箱，再删除 Telegram 消息。任何一步失败都保留必要的消息映射，供用户重试。只有两边完成后才清理正文缓存和映射。走 Cloudflare / Resend 兜底时不显示该按钮。

消息通过 `sendMessage` / `editMessageText` 和 `parse_mode: HTML` 发送。发送层转义正文、保留段落空行，并将验证码转换成 `<code>` 供用户复制。调整渲染方式时须核对段落显示和验证码复制效果。

默认提示词要求描述性文字使用简体中文，验证码等需要复制的值保持原样。链接验证与实际码值分别处理，退订提示只在邮件明确提供相关信息时出现。自定义提示词的占位符替换按字面插入邮件内容，避免正文里的特殊字符被当成替换指令。

三种摘要模式由 `SUMMARY_PROVIDER` 明确选择。OpenRouter 的备用模型切换、ZDR 限制放宽及 reasoning 配置有各自的处理规则，详见 [配置说明](configuration-and-secrets.md)。单次摘要请求的超时覆盖响应头和正文读取，截断响应按失败处理。

原文在本人 Bot 私聊中显示为可读文本，完整排版与附件在备份邮箱查看。

## 验证方法与限制

`pnpm typecheck` 检查类型，`pnpm build` 使用示例配置打包，`pnpm check:public --ref <提交>` 检查指定提交中的公开文件。实际收信、备份和 Telegram 按钮行为按 [运维文档](operations.md#更新部署与回滚) 验证。

验证记录应标明代码版本、日期、运行环境、覆盖场景及脱敏结果。类型检查、打包和本地模拟各有适用范围；外部账号、真实投递和供应商故障需要对应的实际运行证据。

KV 状态合并使用非原子的读改写，`cron:lock` 也只起到降低重复执行概率的作用。并发时可能丢失更新或重复处理、发送通知，当前实现不提供严格的“恰好一次”保证。

生产故障注入需要明确授权和回滚方式。排障记录只保留脱敏后的状态、错误类别和必要元信息，不保存邮件正文、原始 MIME、完整供应商响应或凭据。
